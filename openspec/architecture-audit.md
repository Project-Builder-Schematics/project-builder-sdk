## Warnings (⚠)

- **Pattern**: `scripts/capability-admission.ts` imports `ClosurePath`/`ViolationRule` as `import type` from `scripts/derive-runner-closure.ts`, which in turn imports `capability-admission.ts`'s functions (`buildFileContext`, `classifySurfaceNode`, `enumerateCapabilitySurface`, `resetAnchorExemptionLatch`) as values. This is a genuine type-level back-reference between the two modules — type-erased, so there is no runtime cycle (confirmed: the import is `import type`, and `ViolationRule` is `derive-runner-closure.ts`'s own closed-union type, `RULE_BODIES` and `VIOLATION_RULES` both live there, never duplicated in `capability-admission.ts`). Functionally this is the same "one walk, one classifier-of-classifiers" shape the baseline already tolerates for `classifySpecifier` living beside `derive-runner-closure.ts`'s other helpers; the difference here is the classifier moved to its OWN file and needed the consumer's types back. None of ADR-0079/0080/0081 mentions this arrangement. Not a violation — TypeScript's `import type` erasure makes the coupling free at runtime and the direction of the VALUE dependency (closure-walker → classifier) is the architecturally meaningful one and is correct — but it is undocumented, and the next reader tracing "does `capability-admission.ts` depend on `derive-runner-closure.ts`?" will get a surprising "yes, for two types" answer with no comment explaining why the types weren't hoisted to a shared location (e.g. a `scripts/tripwire-types.ts`, or re-declared locally). Worth a one-line comment or ADR-0079 addendum at the next touch of either file; not worth blocking archive over.

## Judgment: module-scoped exemption latch (`anchorExemptionConsumed`)

`scripts/capability-admission.ts:861` declares `let anchorExemptionConsumed = false` at module scope, consumed by `checkExemption()` and reset by the exported `resetAnchorExemptionLatch()`. This is real mutable module state, which reads as tension against the baseline's characterization of `derive-runner-closure.ts` as "pure, root-parameterised." Traced the actual usage rather than judging the shape in isolation:

- `deriveRunnerClosure()` — the ONE production/test entry point that matters — calls `resetAnchorExemptionLatch()` itself, once per file, **inside** its per-file walk loop (`scripts/derive-runner-closure.ts:163`), immediately before building that file's `FileContext` and classifying its surface. Because the walk visits each closure file exactly once (deduplicated by `nodes.has()`), and the exemption is only ever meaningful on the single designated anchor file (`ctx.exemption` is only set when `isAnchorFile` is true), resetting per-file is observably equivalent to resetting once per whole derivation. **From the outside, `deriveRunnerClosure(distRoot, entryRelPath)` remains referentially transparent**: same inputs, same output, no state leaks across calls, no reentrancy hazard (the code is synchronous, no `await` inside the walk).
- The exported `resetAnchorExemptionLatch()` exists only because `test/fitness/fit-42-runner-closure-integrity.test.ts` calls `enumerateCapabilitySurface`/`classifySurfaceNode`/`buildFileContext` directly, bypassing `deriveRunnerClosure`, to do granular per-node disposition assertions (`assertTotalDispositions`, line ~1015-1030) — and correctly resets before each such call, mirroring production's per-file reset. `test/fitness/fit-42-runner-closure-integrity.negative.test.ts` calls `deriveRunnerClosure()` directly dozens of times across independent `it()` blocks and never needs to touch the reset itself, because the production entry point manages it internally.

**Disposition**: this is a private implementation detail, correctly encapsulated, that does not break the public function's purity contract. It is not the same shape as a pure function internally, but the deviation is confined to a single low-level API surface used only by one test file for one legitimate reason (bypassing the walker to assert per-node totality). Judged **acceptable within the baseline as currently worded** — not a violation, not worth an ADR — but the baseline's "pure, root-parameterised" phrasing for `derive-runner-closure.ts` should be qualified at the next refresh to "pure as observed at the `deriveRunnerClosure` boundary; internally coordinates a per-file exemption latch via `capability-admission.ts`," so a future reader who greps for "pure" and finds `let anchorExemptionConsumed` doesn't independently re-derive this analysis.
