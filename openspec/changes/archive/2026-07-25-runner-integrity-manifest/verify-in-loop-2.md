**Targeted check 3 — "the baseline writer is absent from the build chain" (green-on-arrival)**: ruled **legitimate, but for a different reason than S-000's four rows**, and worth being precise about the distinction rather than mechanically reusing the earlier ruling. S-000's four green-on-arrival rows were each a **necessary, forced corollary** of a driving RED test in the same cycle — there was no way to satisfy the adjacent RED without also satisfying the "free" assertion. ## Assertion Quality Audit (delta)

No banned patterns (`toBeDefined`, `toBeTruthy`/`toBeFalsy` without context, `objectContaining` as the whole assertion, `not.toThrow()` alone, snapshot-only, structure-mirroring mocks, multi-behaviour tests, private-state tests) found in `fit-42`'s new `describe` block or `build-config.test.ts`'s new `describe` block. All assertions pin concrete values or exact array/object shapes.

**One methodological nuance, not a defect**: criterion 1's edge-sortedness check compares `written.edges.map(edgeKey)` (space-joined `"from to specifier"` strings, sorted via `comparePaths`) against itself pre-sorted — this is not literally the same comparator as `compareEdges` (which compares the three fields independently in sequence, short-circuiting on `from`, then `to`, then `specifier`). For all real path/specifier values in this repo (printable ASCII, no character below `0x20`), a space-separated concatenation sorts identically to independent tuple comparison, so the test is sound in practice; it is a proxy for `compareEdges`, not an exact re-implementation of it. Since `regen-closure-baseline.ts` never re-sorts anything itself (it writes `deriveRunnerClosure`'s already-sorted output through unchanged), this test is really verifying "the writer didn't accidentally undo the sort" (e.g., via object-spread key reordering), which it does verify adequately. Not a finding.
